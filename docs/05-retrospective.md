# 05 · 复盘

## 1. 最难的问题：怎么让"不越权"变成结构问题，而不是态度问题

题目把"越权发布或虚报保存成功"定成关键缺陷。这类缺陷的麻烦之处在于：**模型不是想作恶，它是想帮忙**。

真实运行里能看到这种倾向：用户说"18:00 发"，18:00 被占了，模型第一反应是把时段改到 19:00，
然后汇报"已为您调整到 19:00"。从模型视角这是一次成功的任务完成，从业务视角这是**擅自修改了硬性发布要求**。

我试过三条路，前两条都不够：

| 做法 | 问题 |
|---|---|
| 提示词反复强调"不要改用户时间" | 模型会在自己的理由里逻辑自洽："用户要的是当天发布，我保持了当天"。规则描述永远追不上语言的花样 |
| 报告里加一个 `needs_confirmation` 标记 | 标记是模型自己填的。它不填，就没标记；它填了"已排期"，也没人反驳 |
| **把"违规"变成不可表达** | 最终采纳 |

具体三刀：

1. **状态枚举里没有 `published`。** 不是"禁止输出已发布"，而是这套 schema 里根本没有这个值。
   模型想越权，找不到合法的词。
2. **`requested_publish_at` 没有任何写入口。** 7 个业务工具加 finalize，没有一个能改它。想改时段可以，
   但改的结果必然是 `suggested_slot`，而 `requested_slot` 会原样并列出现在同一行。
3. **偏离必须带凭证。** `save_schedule_draft` 内部比较目标时段与用户要求，不一致就要求
   `confirmation_id`，且要校验这个凭证属于本素材、真实存在。凭证由独立的
   `request_confirmation` 产生，模型没法自己编一个 ID 蒙过去。

第 3 条是关键：**把"要不要问人"从模型的判断题，变成了工具的必填项**。

## 2. 第二个问题：报告里的"已保存"凭什么可信

只要报告的字段是模型生成的，"虚报"就永远有缝。所以报告的 `review_status` 和 `draft.status`
改成从两个确定性来源推导：

- `review_status` ← 规则引擎对素材的求值结果（与模型无关）
- `draft.status` ← 工具调用账本里 `save_schedule_draft` 的真实回执

模型的 `decision` 和 `reason` 只作为叙述保留。然后加一段交叉校验：如果模型说
`schedule` 但账本里没有成功回执，就把草稿降级成 `failed`、打上
`CLAIMS_SCHEDULED_WITHOUT_RECEIPT`、整轮标 `incomplete`。

代价是多写约 120 行校验代码，换来的是"信任从模型挪到了代码"。

顺带发现一个反向漏洞：补了 `save_failed` 这个枚举之后，模型可以反过来谎称"保存失败了"
来逃避责任。所以又加了 `SAVE_FAILED_WITHOUT_ATTEMPT`——声称失败但一次都没尝试，同样算撒谎。
**每开一个诚实的出口，都要顺手堵上它变成新出口的可能。**

## 3. 真实模型跑批不可替代

四个真 bug 里三个是真实运行才暴露的：

- 工具参数被长度截断成非法 JSON（`{"date":"` 就断了）→ 循环崩
- 模型把 `decisions` 传成字符串数组 → `AttributeError` 崩
- 模型在 18:00 被拒后，改查 `from_time=19:00` 的空闲时段 → 这一步符合预期，但也说明
  提示词里"查该时段之后"的措辞直接影响行为

脚本化模型（`tests/test_agent_loop.py`）一个都抓不到，因为它永远传合法参数。
这不是说单测没用——单测保证了护栏正确，真实跑批保证了**接口的鲁棒性**。两者缺一不可。

## 4. 学习收获

1. **护栏要在"执行时"重算，不能信模型之前的查询结果。** 保存时重新求值规则，
   否则"先查安全日期、再改到危险日期"就能绕过（TOCTOU）。
2. **幂等指纹要落在语义身份上。** `material_id + date + time + 原始要求`，
   不含 `request_id`——换了请求号也照样认得出是同一件事。
3. **限流是设计输入，不是运维细节。** 20 RPM 直接决定了工具要收数组参数，
   一轮 run 压到 6~9 次调用。先知道这个约束，架构才不会白写。
4. **"待确认"和"已完成"必须是两个字段。** 合成一个 `status`，早晚会把
   "草稿存好了但等人点头"写成"已发布"。

## 5. 不足

- **待确认项不闭环**：只登记，不等待人回答后继续。真实产品需要"人回答 → 重跑该条"的回流。
- **无并发控制**：两个进程写同一 state 文件会互相覆盖。
- **敏感词是字面匹配**：会误伤"最强大脑"这类正常表达，也会漏掉变体写法。
- **样本量小**：8 个用例、单一模型，只能说明这几条路径行为正确，不能外推。
- **崩溃非原子**：整轮运行崩溃时，崩溃前写入的草稿会留在库里（case2 第一次 live 就踩到了）。

## 6. 下一步（按性价比排序）

1. **把 8 个用例变成带断言的回归评测**：现在 `run_examples.py` 只落输出，不断言。
   加一层期望值比对，就能在改提示词时立刻知道有没有回归。
2. **确认闭环**：给 `request_confirmation` 加 `resolve(confirmation_id, answer)`，
   人回答后只重跑受影响的那条素材，而不是整批。
3. **跨模型对比**：同一批用例跑 2~3 个模型，看替代时段的选择是否一致，
   这个差异比单模型跑通更能说明系统的稳定性。
4. **并发安全**：state 加文件锁，或换 SQLite + 事务。

## 7. 实际用时

总计约 **90 分钟**（含等待模型返回、以及三次因缺陷触发的重跑）。按阶段：

| 阶段 | 用时 | 内容 |
|---|---:|---|
| 读题与方案 | ~13 min | 拆验收点、探测端点能力（function calling 与 20 RPM）、定三层架构 |
| 数据与工具层 | ~8 min | 合成素材/规则、规则引擎、护栏、41 条测试 |
| 循环与报告层 | ~7 min | ReAct 循环、trace、verifier 交叉校验 |
| mock + CLI + 用例 | ~12 min | 离线策略、命令行、7 份输入 |
| live 跑批与修缺陷 | ~40 min | 4 轮跑批；修掉参数截断、`_as_list`、枚举缺口、卡死保护 |
| 文档与示例整理 | ~15 min | 5 份文档、trace 渲染、对照表 |

时间主要花在 **live 跑批后的缺陷修复**上，而不是写代码。这也符合预期：护栏和幂等这类逻辑
写起来快、测起来慢，而模型输出的畸形参数只有在真实调用里才会出现。
